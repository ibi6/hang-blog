React 18 的并发特性已经稳定了一段时间，在真实业务里落地时仍然有一些不那么"官方示例"的坑。这篇记录我过去半年里遇到的三类问题与它们的解法。

## 问题 1：useTransition 没有让输入更顺滑

官方的示例通常用一个 10000 行的列表展示 `useTransition` 的威力，但在实际业务中，卡顿的来源常常不是渲染本身，而是状态更新触发了一个同步的 IO 操作。

```tsx
const [isPending, startTransition] = useTransition();
const [query, setQuery] = useState("");

function onChange(e: React.ChangeEvent<HTMLInputElement>) {
  setQuery(e.target.value);
  startTransition(() => {
    // 这里真的有重计算吗？别自我安慰
    setResults(filter(data, e.target.value));
  });
}
```

### 需要先 profile，再决定

在我遇到的几个案例里：

- 如果过滤逻辑是 O(n) 纯 JS，`useTransition` 效果显著
- 如果过滤发生在 Web Worker 之外的任何异步 IO 上，`useTransition` 几乎无作用
- 真正的瓶颈往往是大列表未虚拟化

> 经验法则：先用 React DevTools 的 Profiler 量一量再上并发 API。

## 问题 2：Strict Mode 下的双重 effect

开发环境里 Strict Mode 会故意调用两次 effect，这在依赖订阅的代码里会表现为"多订阅了一份"。解决办法是保证 cleanup 的完整性：

```ts
useEffect(() => {
  const sub = source.subscribe(handler);
  return () => sub.unsubscribe();
}, []);
```

只要每次订阅都能被对应的 cleanup 取消，Strict Mode 的双调用就是一件好事。

## 问题 3：Suspense 与数据获取的组合

在推荐的数据流里，Suspense 配合 React Query 或 Relay 时工作得非常好；但在自建的数据层里，要特别留意：

1. 不要在渲染阶段直接抛 Promise（除非你知道自己在做什么）
2. 加载边界要画得足够小，避免"一个组件抛错导致半个页面白屏"
3. 记得给 `ErrorBoundary` 搭档，否则 Suspense 是个只会装死的黑洞

## 小结

React 18 带来的并发能力是工具，不是银弹。更多优化机会其实来自「先测量，再决定」的朴素工程习惯。
